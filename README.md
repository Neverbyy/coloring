# Раскраска — веб-версия

Детская раскраска на Nuxt 4 + TypeScript. ТЗ — [docs/TZ.md](docs/TZ.md).

## Запуск

```bash
npm install
cp .env.example .env   # вписать строки подключения к Postgres
npm run db:migrate     # таблицы и базовые арты
npm run dev            # http://localhost:3000
npm run typecheck
npm run build
```

## База данных

- Postgres в Supabase, доступ только с сервера через Drizzle ORM (`postgres.js`). Supabase Auth и `supabase-js` не используются: вход свой (страна + имя).
- Приложение подключается через transaction pooler (порт 6543, `NUXT_DATABASE_URL`, без prepared statements — так требует pooler). Миграции идут через session pooler (порт 5432, `DATABASE_MIGRATION_URL`).
- Строка подключения задаётся только при запуске (`runtimeConfig`) и в сборку не попадает.
- На всех таблицах включён RLS без политик: REST API Supabase с публичным ключом к ним доступа не имеет, сервер подключается ролью `postgres` и RLS обходит.
- Схемы лежат рядом с кодом: таблицы игры — в `layers/<игра>/server/db/schema.ts` с префиксом игры (`coloring_arts`). Миграции — `server/db/migrations` (`npm run db:generate` после изменения схемы, `npm run db:migrate` для применения).
- Деплой: в Vercel задать `NUXT_DATABASE_URL`, регион функций — `dub1` (база в eu-west-1, Ирландия). Миграции применяются вручную перед деплоем.

## Структура

- `app/` — общая часть платформы: вход (`/login`), глобальные стили, плагин «нативности».
- `layers/coloring/` — игра «Раскраска» как отдельный Nuxt-слой: галерея (`/coloring`), экран рисования (`/coloring/[id]`), компоненты, стор инструментов, палитра. Новая мини-игра добавляется ещё одним слоем в `layers/` без правок общей части.
- `shared/utils/` — код, общий для клиента и сервера (список стран, проверка имени).

## Принятые решения

**Экраны и адаптив**

- **Отступление от макета: на телефоне игра только вертикальная.** Мобильные фреймы в макете горизонтальные (844×390), но на телефоне с панелью браузера горизонтальный экран получается слишком низким. К тому же игроку с выключенным автоповоротом приходилось разбираться с ориентацией. Поэтому сделано как в мобильных веб-играх (например, в Яндекс Играх):
  - экран рисования на телефоне вертикально (ширина < 600px): сверху дом и камера, посередине холст, внизу полоса — инструменты слева, цвета справа, карандаши остриём вверх. Палитра работает как в ТЗ: инструменты уезжают вниз, цветные карандаши по очереди выезжают на их место, полоса листается вбок;
  - телефон горизонтально (сенсорный экран ниже 500px) — экран закрыт подсказкой «Поверни телефон» на всех страницах. Работает на чистом CSS, видна сразу, ещё до загрузки скриптов;
  - планшеты и компьютеры — горизонтальная раскладка из макета без изменений (совпадает с Figma до пикселя).
- Полноэкранного режима нет: пробовали (Fullscreen API на Android), но в вертикали панель браузера отнимает немного места, а автоматический переход в полный экран неожиданен для игрока. Ориентацию сайт без полного экрана зафиксировать не может, поэтому в горизонтали работает подсказка «Поверни телефон».
- Панель инструментов и цветов подстраивается под свою длину (высоту колонки или ширину полосы): если места мало, карандаши пропорционально уменьшаются, но не мельче 72% (~32px, чтобы попадать пальцем). Если не хватает и этого, показывается меньше недавних цветов. Кнопки отмены и повтора при высоте экрана до 360px — 44px.
- Экран рисования: до 1024px доска занимает весь экран, на десктопе — не больше 1280×920 по центру со скруглением (как в макете 1320).
- Галерея: не больше 4 колонок (как в макете), на узких экранах колонок меньше, но карточки не уже 140px. Сетка по центру, если помещается; иначе прокручивается внутри экрана.
- Галерея постраничная: 12 карточек на странице — карточка импорта (есть на каждой странице) и 11 артов. При большем количестве внизу появляется пагинация. Номер страницы хранится в адресе (`?page=2`), поэтому переживает обновление страницы. Данные идут через TanStack Query: первая загрузка приходит готовой с сервера (SSR), следующая страница подгружается заранее, при переключении предыдущая остаётся на экране до ответа. Номер вне диапазона сервер заменяет ближайшей существующей страницей.
- Страницы галереи кэшируются на 5 минут: при переключении туда-обратно повторных запросов нет. Галерея меняется только действиями игрока, и они сбрасывают кэш сами: импорт и удаление — всю галерею, выход из арта — только страницу, где лежит этот арт (новые процент и миниатюра на карточке видны сразу из памяти вкладки).
- Если страниц несколько, карточки стоят от верха, а пагинация прижата к низу экрана (или идёт сразу под карточками, если они не помещаются): на неполной последней странице ничего не прыгает. Одна страница — сетка по центру, как в макете.
- На экранах до 680px (телефоны, узкие планшеты) пагинации нет: галерея — лента экранов, которые листаются свайпом (как рабочий стол телефона), внизу точки (на них можно нажать). На экране столько карточек, сколько влезает: колонки — из той же сетки, ряды — по высоте. Страницы API подгружаются по мере листания (TanStack `useInfiniteQuery`, начиная с уже загруженной первой), ещё не загруженные карточки — заглушки. Карточки прижаты к верху: первый экран из SSR (обрезан по целым рядам через CSS `round()`) совпадает с тем, что потом разложит скрипт, — без скачка при загрузке. После возврата из арта открывается тот же экран. Предзагрузка рисунка по нажатию на карточку срабатывает через 100 мс удержания или на отпускании: свайп по карточке её не запускает.
- Учтены вырезы iPhone (safe area): карандаши справа уходят под вырез, кнопки слева от него отступают.
- Экран входа сделан сами в стилистике макета: страна (список ISO 3166-1, страна по умолчанию — по языку браузера) и имя.
- Страна выбирается в своём выпадающем списке, а не в `<select>`: нативный не показывает картинки и не ограничивает высоту, а эмодзи-флагов нет в Windows. Флаги — SVG из пакета `flag-icons`, раздаются как статика `/flags/<код>.svg` и грузятся лениво при прокрутке (все вместе ~1.9 МБ). Есть поиск и управление с клавиатуры. Меню открывается вниз или вверх — где больше места, а на низком экране (телефон горизонтально) — на всю высоту поверх формы.

**Панели инструментов и цветов**

- В макете 8 карандашей отдельными картинками; для 32 цветов используется один рисунок карандаша с подменой цвета. Активный предмет выдвинут на 30px — так в макете отличаются ширины 90 и 60.
- Выбранный инструмент переезжает наверх, остальные анимированно перестраиваются.
- Под активным цветом видны два недавних. Нажатие на активный карандаш открывает палитру: инструменты уезжают, карандаши выезжают по очереди снизу вверх, список прокручивается. Выбор цвета закрывает палитру; закрыть её можно и касанием рисунка или клавишей Esc.
- Цвета показываются тем, чем рисуют: при кисти внизу и в палитре кисточки разных цветов, при карандаше — карандаши. При смене инструмента предметы по очереди уезжают за край и возвращаются в новом виде.
- Активные кисть и карандаш в блоке инструментов окрашены в выбранный цвет (ворс и корпус), неактивные — чёрные, как в макете. Инструмент и цвет считываются одним взглядом на верхний предмет.
- У резинки цвета нет: при её выборе цвета уезжают за край и возвращаются, когда снова выбраны кисть или карандаш.
- 8 цветов взяты из макета, остальные 24 подобраны сами.

**Рисование**

- Сегменты определяются по самой картинке, одинаково для PNG и SVG. Картинка растеризуется в рабочий холст (длинная сторона 1024), тёмные пиксели считаются линиями, связные светлые области между ними — сегментами. Так раскрашивается любая картинка с замкнутыми контурами, в том числе незнакомый проверочный SVG.
  - Крошечные области (щели на стыках линий, меньше 48 пикселей) своими сегментами не считаются: их краску получает соседний сегмент, иначе на стыках оставались бы белые точки.
  - Краска заходит под линию на 3 пикселя — между цветом и контуром нет светлой каймы.
  - Разрывы в линиях до ~6 пикселей (на картинке 1024) закрываются: у рисунков «из интернета» (трассированные PNG) линии часто прерываются, и через разрыв области сливались — например, кузов машины с фоном. Сначала находятся «ядра» областей — пиксели дальше 3 пикселей от линий, затем все ядра одновременно разрастаются и встречаются посередине разрыва. Узкие замкнутые места без ядра остаются отдельными областями. Порог подобран так, что разметка трёх базовых артов не изменилась ни на пиксель; при большем пороге узкие проходы (щёки между усами кошки, камни у дома) начинали делиться на части. Разрывы шире закрыть нельзя без ложных разрезов — такие картинки стоит перерисовать или трассировать в чёрно-белом режиме.
  - Области, касающиеся края картинки, — фон. Его можно красить, но в процент заполнения он не входит, иначе 100% было бы почти недостижимо.
- Штрих обрезается маской сегмента, в котором начался: пока палец или кнопка мыши не отпущены, линия не выйдет за его контур. Касание на толстой линии относится к ближайшему сегменту (до 10 точек).
- Удержание кисти или карандаша на месте 0.45 с (сдвиг меньше 10px) заливает весь сегмент, удержание резинки очищает его. Под пальцем при удержании сужается кольцо цвета, так что видно, что сейчас произойдёт.
- Кисть — широкая (34 точки), сплошная и непрозрачная, как гуашь. Карандаш — тонкий (12 точек), полупрозрачный, с зерном бумаги. Резинка тоже не выходит за сегмент.
- Контур картинки лежит поверх краски (`mix-blend-mode: multiply`): линии остаются чёткими, белое прозрачно.
- Рисунок вписан в рамку с отступом снизу под кнопки отмены и повтора. В макете они перекрывали низ картинки, и там было бы не закрасить.
- Красить можно во всей рамке, а не только в квадрате картинки. Холст — это «бумага»: картинка плюс поля вокруг, а на экране видна та её часть, что попадает в рамку.
  - Поля при разметке соединяются с фоном картинки, то есть это тот же сегмент фона, и в процент он не входит.
  - Размер бумаги зависит только от арта, не от экрана (1632×2560 для квадратной картинки), поэтому история рисунка одинакова на телефоне и компьютере.
  - Бумага покрывает области рисунка с соотношением сторон от 0.5 до 1.6. На очень широких и низких экранах (ноутбук 1366×657, окно 844×390) доска поэтому становится уже и стоит по центру.
  - Камера и миниатюра берут область картинки.

**История и сохранение**

- История — журнал операций: штрих (инструмент, цвет, точки), заливка, очистка. Операция хранит точку, а не номер сегмента: растеризация в разных браузерах чуть отличается, и номера областей могли бы разъехаться.
- Хранение рассчитано на рост: **одна строка на рисунок** (игрок + арт) в `coloring_drawings`, а не строка на каждый штрих. В строке:
  - базовое изображение (PNG краски);
  - последние операции после него (`jsonb`, не больше ~70);
  - позиция отмены, процент и миниатюра для галереи.
- Отменить можно минимум 50 последних действий — для детской раскраски с запасом. Когда операций становится 70, самые старые 20 «запекаются» в базовое изображение: оно собирается на невидимом холсте в фоне, игрок продолжает рисовать. Объём строки ограничен, сколько бы ни рисовали.
- Для быстрой отмены браузер держит в памяти снимки холста не реже чем через 20 операций. Отмена — это ближайший снимок плюс доигрывание не больше 20 операций, поэтому она не замедляется. Повтор просто выполняет следующую операцию.
- Журнал и позиция отмены хранятся на сервере, так что undo/redo продолжаются после перезагрузки. Новое действие после отмены отбрасывает отменённые, как в редакторах.
- Автосохранение: изменения уходят на сервер через 0.7 с после последнего действия, серия штрихов — одним запросом. Запрос идемпотентен: «заменить операции после N на эти», поэтому повтор после сбоя безопасен.
- Без сети работа не теряется. Несохранённое сразу пишется в `localStorage` — только то, чего нет на сервере (обычно 0–3 действия), а новое базовое изображение, пока оно не дошло, — отдельно и один раз. Запрос повторяется с нарастающей паузой (до 30 с) и сразу при появлении сети. Игрок видит «Нет связи — сохраним позже». Если закрыть вкладку до отправки, всё уйдёт на сервер при следующем открытии рисунка.

**Галерея**

- Карточка показывает рисунок игрока: после изменений браузер делает миниатюру (JPEG, вся бумага с полями, ~720px по длинной стороне) и отправляет её вместе с автосохранением. Карточка раскладывает её как экран рисования: картинка вписана на своё обычное место, закрашенные поля заполняют карточку до краёв. Адрес миниатюры содержит версию (`?v=время`), поэтому браузер кэширует её навсегда и скачивает заново только после изменений.
- Процент и миниатюра приходят с сервера сразу в HTML. Рамка-прогресс построена на чистом CSS (размеры через единицы `cq`, длина контура через `calc()`), поэтому видна без скриптов, до загрузки JavaScript. В браузерах без такой поддержки те же формулы считает скрипт.
- После выхода из арта карточка обновляется сразу (~0.1 с): свежая миниатюра и процент берутся из памяти вкладки, не дожидаясь ответа сервера.
- Арт открывается без белого холста.
  - Пока грузится состояние, на месте холста — миниатюра рисунка. Она уже есть у браузера, а при открытии по ссылке приходит в HTML с сервера.
  - Данные арта берутся из кэша галереи.
  - Состояние рисунка и базовое изображение начинают грузиться параллельно в момент нажатия на карточку, ещё до перехода. Холст готов примерно вдвое быстрее, чем раньше: 0.67 с вместо 1.44 с на dev-сервере.
  - При уходе со страницы этот кэш удаляется — повторное открытие всегда показывает последние штрихи.
- Работа с двух устройств одновременно — «последнее сохранение побеждает».
- На компьютере работают Ctrl+Z и Ctrl+Shift+Z / Ctrl+Y.

**Производительность при долгом рисовании**

Проверено нагрузочным тестом: 150 каракулей на одном арте. Было: 9 → 12 долгих задач (>50 мс) от начала к концу сессии и кадры до 67 мс. Стало: ни одной долгой задачи, кадры ≤ 17 мс (60 кадров/с) и в начале, и в конце. Что для этого сделано:
- Процент считается по копии на отдельном холсте. Если часто читать пиксели с видимого холста, Chrome переводит его с видеокарты на процессор, и рисование на большой бумаге тормозит — это и была главная причина лагов.
- Точки касания (включая промежуточные, для гладкой линии) копятся и рисуются раз в кадр. Маска сегмента накладывается только на кусок под пальцем, а не целиком: у фона маска размером со всю бумагу.
- Миниатюра и картинка для камеры собираются в паузе (1.5 с без действий, когда браузер простаивает). На компьютере картинка для камеры делается по нажатию.
- Отмена доигрывает операции без промежуточных подсчётов процента — он считается один раз в конце.

**Прогресс и завершение**

- Процент — по площади сегментов (без фона). Сегмент, закрашенный на 95% и больше, считается закрашенным полностью: пальцем не дотянуться до каждого пикселя у контура. Резинка процент уменьшает.
- Рамка — «дорожка» (`#CDF4FF`), заполнение рисуется поверх неё более насыщенным голубым (`#36A9E8`, в макете только 0%) от 180° против часовой стрелки. Тот же прогресс — на карточке в галерее.
- Процент «0%» прижат к правому краю: в макете у «0%» зафиксирован левый край, и «100%» уехало бы за рамку.
- 100%: короткая встряска камеры, «Готово!», процент становится оранжевым, камера покачивается, подсказывая сохранить картинку. Время первого завершения сохраняется (для статистики).

**Сохранение картинки**

- Камера отдаёт PNG рисунка без интерфейса: белая бумага, краска и контур. На телефоне открывается системное «Поделиться», в нём же «Сохранить изображение». На компьютере, и там, где «Поделиться» с файлами нет, файл скачивается.
- Сохранить прямо в галерею телефона без подтверждения браузер не позволяет — это ограничение платформы.
- PNG готовится заранее, через 0.8 с после изменения: Safari не даёт открыть «Поделиться», если внутри нажатия долго ждать.

**Пользователи и вход**

- Вход без пароля, по стране и имени, как в ТЗ. Имя уникально на весь сервис без учёта регистра («Masha» и «masha» — один игрок). Совпали имя и страна — это тот же игрок, он продолжает свою работу. Имени нет — создаётся новый игрок. Имя занято игроком из другой страны — «Это имя уже занято — придумай другое».
- Принятый риск: кто знает имя и страну игрока, тот войдёт под ним. Это следует из требования «без пароля».
- Имя: 3–20 символов, буквы любого алфавита, цифры и `_ . -`. Проверяется одной функцией на клиенте и на сервере (`shared/utils/username.ts`).
- Сессия — случайный токен в httpOnly-cookie (JavaScript страницы её не прочитает) на 180 дней. Срок продлевается, пока игрок заходит. В базе хранится только SHA-256 токена: утечка таблицы не даёт войти под чужой сессией.
- Все страницы, кроме входа, и все `/api/coloring/*` требуют сессию. Страницы закрывает глобальный middleware, данные — проверка на сервере в каждом обработчике (`requireUser`). Гость, открывший ссылку на арт, после входа возвращается на неё. Если сессия закончилась во время игры, следующий запрос возвращает на вход.
- При смене игрока в той же вкладке кэш запросов очищается — данные разных игроков не смешиваются.

**Импорт своего SVG**

- Карточка «+» в галерее: выбрать файл или (на компьютере) перетащить его на карточку. Принимаются только SVG до 1 МБ; другой файл сразу получает понятное сообщение внизу экрана, приложение работает дальше.
- SVG готовится к раскраске на сервере (`layers/coloring/server/utils/svgArt.ts`, библиотека `svgo`) и превращается в «контур»: каждая фигура — белая область с чёрной обводкой. Дальше это обычный арт: сегменты, процент, история и миниатюры работают так же, как у PNG.
  - Цвета, градиенты и прозрачность из Figma не переносятся: раскраска начинается с чистого листа.
  - Порядок фигур сохраняется: что в Figma закрыто верхней фигурой, закрыто и в раскраске. Пересечения фигур дают отдельные области.
  - Фигуре без обводки добавляется обводка, слишком тонкие обводки утолщаются (иначе линия рвётся и краска перетекает в соседнюю область). Пунктир становится сплошной линией.
  - Прямоугольник фона фрейма Figma (без обводки, во весь рисунок) убирается: иначе весь рисунок был бы одной областью.
  - Линии пера без заливки работают тоже: области образуют пересечения и замкнутые контуры.
  - Чёрные и почти чёрные заливки (яркость < 35%) остаются чёрными — это сами линии. Так устроены трассированные картинки (potrace, «векторизация» PNG): контур там — залитая чёрная фигура, а не обводка. Принятый риск: большая тёмная фигура из Figma тоже останется чёрной, а не станет областью для раскраски.
  - Трассированная картинка из нескольких оттенков серого (VTracer и т. п.: «стопка» заливок, линии — тёмные места между светлыми кусками) распознаётся отдельно: в файле нет обводок, все цвета серые, есть тёмные заливки. Тогда фигуры не обводятся, а каждая становится чёрной или белой по яркости — как в оригинале. Иначе каждый кусок получил бы рамку; например, «шахматка» фальшивой прозрачности, нарисованная в скачанном PNG, превращалась в сетку. Качество линий такого файла зависит от исходного PNG: из маленькой картинки получаются рваные края.
  - Толщина обводок учитывает масштаб из `transform` (у трассированных SVG координаты часто увеличены в 10 раз и уменьшены `scale(0.1)`).
  - Внутренние и внешние обводки Figma (маски) сохраняются как есть.
- Безопасность: белый список элементов (фигуры, группы, маски, обрезки) и атрибутов. Удаляются скрипты, `foreignObject`, обработчики `on*`, стили, ссылки на внешние ресурсы, `DOCTYPE` с сущностями отклоняется. SVG отдаётся только владельцу с заголовками `Content-Security-Policy: default-src 'none'` и `nosniff` — даже открытый напрямую, он не выполнит скрипт.
- Понятные сообщения вместо ошибок: не SVG или повреждён, больше 1 МБ, нет размера, слишком вытянутый (больше 8:1), больше 5000 фигур, только текст или картинки. Текст и вставленные растровые картинки пропускаются с сообщением (в Figma текст при экспорте и так обычно переводится в контуры).
- После подготовки браузер размечает рисунок той же функцией, что и экран рисования. Если областей для раскраски нет (например, одна незамкнутая линия), арт удаляется и игрок видит «замкни контуры фигур».
- Импортированный арт виден только своему игроку, появляется первым в галерее (сразу после «+») и удаляется крестиком на карточке с подтверждением «Удалить?» — детям легко нажать случайно. Вместе с артом удаляются рисунок и несохранённый хвост в браузере. Своих артов — до 50.
- Один и тот же рисунок дважды не загрузить: сервер хранит SHA-256 подготовленного SVG, а уникальный индекс «игрок + отпечаток» отклоняет повтор с сообщением «Этот рисунок уже есть в твоей галерее». Отпечаток считается от результата подготовки, поэтому тот же файл под другим именем или с другим форматированием тоже распознаётся; двойное нажатие не создаст копию. У разных игроков один и тот же рисунок не конфликтует.

**«Нативность»**

- Нет скролла страницы, pull-to-refresh, выделения текста, зума (щипок, двойной тап), перетаскивания картинок и меню по долгому тапу.

## Пока заглушки

- Три базовых арта (осьминог, кошка, дом) — PNG.
- Выхода из аккаунта в интерфейсе нет (в макете нет места под него) — только API `POST /api/auth/logout`.
