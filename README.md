# Раскраска — веб-версия

Детская раскраска на Nuxt 4 и TypeScript. Игрок входит по стране и имени, выбирает арт в галерее или импортирует свой SVG и раскрашивает его. История действий хранится на сервере, рисунок можно сохранить или отправить. Для администратора есть админка со статистикой. ТЗ — [docs/TZ.md](docs/TZ.md).

## Доступ

| | Адрес | Как войти |
|---|---|---|
| Игра | `https://coloring-steel.vercel.app` | Выбрать страну и ввести любое имя: 3–20 букв любого алфавита, без цифр, пробелов и знаков. Игрок создаётся при первом входе. Чтобы вернуться к своим рисункам, войдите с тем же именем и страной |
| Админка | `https://coloring-steel.vercel.app/admin` | Логин `admin`, пароль `bfXZGDxfZO9wHD2hPfzi4vE0`. Своего администратора можно создать командой `npm run admin:create -- <логин>`, повторный запуск с тем же логином сбрасывает пароль |

- **Игра:** на телефоне вертикально, на планшете и компьютере. Если держать телефон горизонтально, игра просит его повернуть.
- **Админка:** на любом экране от 350px.

## Локальный запуск

Нужны Node.js 22.12+ (Nuxt советует 22.22+) и база Postgres. Проект работает с Supabase, но подойдёт любой Postgres.

```bash
npm install
cp .env.example .env              # строки подключения к базе
npm run db:migrate                # таблицы и три базовых арта
npm run admin:create -- admin     # администратор: печатает случайный пароль, повторный запуск — сброс
npm run dev                       # http://localhost:3000
```

Проверки:

```bash
npm test             # автотесты (Vitest), без базы и браузера
npm run typecheck    # типы
npm run build        # прод-сборка
```

Переменные `.env`:
- `NUXT_DATABASE_URL` — подключение приложения. В Supabase это transaction pooler, порт 6543.
- `DATABASE_MIGRATION_URL` — подключение для миграций. В Supabase это session pooler, порт 5432.
- `NUXT_PUBLIC_SUPABASE_URL`, `NUXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NUXT_SUPABASE_SECRET_KEY` — Supabase Realtime: сигнал «галерея изменилась» после правок в админке. Адрес и publishable-ключ публичные и уходят в браузер, secret — только на сервере. Без них всё работает, галерея просто обновляется по кэшу, как раньше. Сама база — напрямую через Postgres, не через API Supabase.

Деплой — Vercel из git:
- в Vercel задаются `NUXT_DATABASE_URL` и три переменные Supabase Realtime;
- регион функций — `dub1`, рядом с базой в eu-west-1;
- миграции применяются вручную до деплоя.

## Архитектурные решения

**Модульная архитектура (модульный монолит).** Приложение одно — один деплой и одна база, — но внутри разделено на модули с чёткими границами:
- **платформа** (`app/`, `server/`, `shared/`): вход, сессии, админка, звук, общие стили;
- **игра «Раскраска»** — отдельный модуль, Nuxt-слой `layers/coloring/`. У неё свои страницы, компоненты, API, таблицы с префиксом `coloring_*` и разделы админки.

Зависимости идут в одну сторону: игра пользуется платформой, а платформа не импортирует ничего из игры. Игра сама встраивается в платформу:
- страницы встают в маршруты по путям файлов;
- музыка экранов задаётся через `meta.music`;
- разделы админки и вкладка на странице игрока подключаются из `app.config.ts` слоя (`admin.sections`, `admin.userTabs`), а их страницы кладутся в `pages/admin/…` слоя.

Новая мини-игра — ещё один слой в `layers/`, без правок платформы. Внутри модуля код разложен по стандартной структуре Nuxt: `pages`, `components`, `composables`, `stores`, `server/api`. Движок рисования (`engine/`) — чистый TypeScript без Vue, компонент холста — только тонкая обёртка над ним.

**К данным ходит только сервер.** База — через Drizzle ORM и `postgres.js`. Supabase Auth и `supabase-js` не используются.
- На всех таблицах включён RLS без политик, поэтому публичный ключ Supabase к данным не пускает.
- Строка подключения задаётся только при запуске и в сборку не попадает.
- Каждый защищённый обработчик проверяет сессию сам: `requireUser` у игрока, `defineAdminHandler` в админке.

**Запросы к базе без конвейера.** По умолчанию `postgres.js` отправляет запрос в уже занятое соединение, а transaction pooler Supabase разводит такие запросы по разным соединениям с базой. Под нагрузкой ответы приходили не тем запросам, а часть запросов зависала. Поэтому:
- у обычных запросов конвейер выключен (`max_pipeline: 0`);
- транзакциям он нужен для внутренней работы драйвера, поэтому у них отдельный небольшой пул, а соединение на время транзакции закреплено за ней.

Проверено нагрузкой: 72 параллельных запроса вместе с транзакциями прошли с верными ответами. Со старой настройкой не прошла ни одна группа.

**Серверный рендер без скачков.** Галерея и экран рисования приходят из SSR уже с данными. TanStack Query подхватывает их в браузере без повторного запроса. Рамка прогресса нарисована на чистом CSS, поэтому видна ещё до загрузки скриптов.

**Рисование по растру.**
- Картинка SVG растрируется, тёмные пиксели считаются линиями, светлые области между ними — сегментами. Так раскрашивается любая картинка с замкнутыми контурами, в том числе незнакомый SVG на проверке.
- Штрих обрезается маской сегмента, в котором начался.
- Операция истории хранит точку касания, а не номер сегмента: растрирование в разных браузерах чуть отличается.
- Холст — это «бумага»: картинка плюс поля. Её размер зависит только от арта, поэтому история одинакова на любом устройстве.

**Импорт SVG.**
- **Сервер** (`svgo`) оставляет только разрешённые элементы и атрибуты и превращает рисунок в контур: белые области и чёрные линии.
- **Браузер** размечает результат той же функцией, что холст. Если раскрашивать нечего, импорт отменяется.
- **Отдача.** SVG отдаётся с `Content-Security-Policy: default-src 'none'`.
- **Повторы** отсекаются по SHA-256 подготовленного SVG.

**Вход.**
- **Игрок** входит без пароля, как требует ТЗ: сессия — случайный токен в httpOnly-cookie, в базе хранится только его SHA-256.
- **Администраторы** — отдельная таблица с ролью `admin`, а не флаг у игроков. Пароль хранится как scrypt с солью. После 5 ошибок подряд вход закрыт на 15 минут. У админа своя cookie, которая отправляется только на `/api/admin`.
- **Второй замок.** Серверный middleware раскодирует и нормализует путь, поэтому `/api/%61dmin/…` и `//api/admin/…` тоже закрыты.

**Звук.** Эффекты играют через Web Audio: малая задержка и бесшовная петля. Музыка — один `<audio>` на всё приложение, поэтому при переходе между экранами она не прерывается. Когда страница уходит в фон (свернули браузер, переключили вкладку, закрыли), музыка сразу встаёт на паузу без затухания. Затухание работает на `requestAnimationFrame`, а в фоне браузер его не вызывает — раньше из-за этого музыка продолжала играть. Эффекты (`AudioContext`) при этом приостанавливаются. Вернулся игрок — музыка продолжается с того же места.

## Модель хранения состояния и истории

### Сервер (Postgres)

| Таблица | Что хранит |
|---|---|
| `users`, `sessions` | игроки (имя уникально без учёта регистра) и их сессии (SHA-256 токена, срок 180 дней, продлевается) |
| `admins`, `admin_sessions` | администраторы (хеш пароля, счётчик ошибок входа) и их сессии (7 дней) |
| `coloring_arts` | арты: название, размер, статус (`published` + `published_at`), «кому показывать» (`audience`), у импортов — владелец, SVG и его отпечаток |
| `coloring_art_countries`, `coloring_art_users` | кому назначен арт: страны и отдельные игроки |
| `coloring_drawings` | рисунок игрока — одна строка на пару «игрок + арт» |
| `coloring_art_opens` | журнал открытий экрана рисования для статистики |

Одна строка `coloring_drawings` — это весь рисунок:
- базовое изображение (PNG краски);
- последние операции после него (`jsonb`);
- позиция отмены (`cursor`) и процент заполнения;
- миниатюра для галереи (JPEG);
- `started_at` и `completed_at` для статистики.

Строк на каждый штрих нет, поэтому объём не растёт с длительностью рисования.

### История и отмена

- **Операции:** штрих (инструмент, цвет, точки, толщина, прозрачность), заливка сегмента (кисть или карандаш, прозрачность), очистка сегмента, сброс всего рисунка. Сервер принимает толщину и прозрачность только из заданных наборов; старые операции без этих полей рисуются как раньше. Номера операций сквозные. Действие, которое ничего не изменило (резинка по пустому, сброс чистого холста), в историю не попадает.
- **Отмена.** Отменить можно минимум 50 последних действий. Когда операций становится 70, самые старые 20 «запекаются» в базовое изображение: его собирает невидимый холст в фоне.
- **Скорость отмены.** Браузер держит в памяти снимки холста не реже чем через 20 операций. Отмена — это ближайший снимок и доигрывание не больше 20 операций, поэтому она не замедляется.
- **Сохранение** устроено как «заменить операции после N на эти» и идемпотентно: повтор после сбоя безопасен.
  - 409 — история разошлась с сервером: клиент выравнивается и отправляет заново.
  - 413 — история слишком длинная: клиент отправляет новую базу.
- **После перезагрузки** undo/redo продолжаются с той же позиции: журнал и курсор хранятся на сервере.
- **Два устройства.** При работе с двух устройств одновременно побеждает последнее сохранение.

### Браузер

- **Автосохранение.** Изменения уходят на сервер через 0,7 с после последнего действия. Без сети неотправленный хвост лежит в `localStorage`, а новая база — отдельно, пока не дошла. Повторы идут с растущей паузой до 30 с и сразу при появлении сети. Если закрыть вкладку до отправки, хвост досылается при следующем открытии рисунка.
- **Уход из рисунка.** Несохранённое и свежая миниатюра для галереи отправляются сразу. Если в этот момент уже идёт отправка, они ждут её окончания: иначе старая миниатюра могла дойти до сервера позже новой. История уходит с `keepalive` (переживёт закрытие вкладки), только если укладывается в его лимит — 64 КБ на все такие запросы сразу. Миниатюра (JPEG до ~150 КБ) в лимит не помещается и идёт обычным запросом. Раньше она тоже шла с `keepalive`, браузер молча её отклонял, и после быстрого выхода из рисунка в галерее на других устройствах и после перезагрузки оставалась старая картинка.
- **Кэш галереи** (TanStack Query) живёт 5 минут. Импорт и удаление сбрасывают всю галерею, выход из арта — только страницу с ним. Правки админа приходят сразу — см. ниже.
- **Правки админа видны сразу.** Когда админ публикует, скрывает, переименовывает опубликованный арт или меняет, кому его показывать, сервер шлёт в Supabase Realtime сигнал «галерея изменилась» (REST broadcast с секретным ключом, канал `coloring-gallery`). Браузер вошедшего игрока держит WebSocket на этот канал и по сигналу сбрасывает кэш галереи. Открытая галерея перезапрашивается сразу, остальные экраны — при возврате в неё. В проверке новая карточка появилась через ~1 с после публикации.
  - **В сигнале нет данных.** Каждый браузер запрашивает свой список у нашего API, и права проверяет наш сервер. Арт, назначенный одному игроку, другим не покажется.
  - **Почему не SSE.** Сервер на Vercel — короткоживущие функции. Админ публикует на одном экземпляре, а игроки подключены к другим, поэтому нужен общий канал. Каждое открытое SSE-соединение — работающая и оплачиваемая функция, которую обрывает лимит времени. `LISTEN/NOTIFY` Postgres через transaction pooler не работает. Realtime у Supabase уже есть, и он рассылает сигнал всем подключённым.
  - **Канал публичный.** Подписаться на него и отправить в него событие может любой, у кого есть публичный ключ. Поэтому перезапрос по сигналу — не чаще раза в 5 с и с разбросом до 1,5 с, чтобы все игроки не спрашивали сервер одновременно. Поток поддельных сигналов превращается в редкий лёгкий перезапрос своей же галереи.
  - **Обрывы.** Клиент `@supabase/realtime-js` сам переподключается. После повторного входа в канал галерея перезапрашивается: события, пропущенные за время обрыва, не теряются.
- **Сторы Pinia:** игрок, администратор, инструмент и цвет, музыка.
- **Cookies:** `session` (игрок), `admin_session` (только `/api/admin`), `music` (включена ли музыка — значок верный уже в HTML с сервера), `quick_login` (быстрый вход: до 4 игроков — имя, страна, время последнего визита).

## Решения по продукту и отступления от макета

**Экраны.**
- **Телефон — только вертикально.** Это отступление от макета: мобильные фреймы в нём горизонтальные, но с панелью браузера горизонтальный экран слишком низкий.
  - Вертикально: сверху дом и камера, внизу полоса: цвета слева, инструменты справа.
  - Горизонтально: экран закрыт подсказкой «Поверни телефон». Она сделана на чистом CSS и видна сразу.
- **Планшеты и компьютеры** — раскладка из макета, сверена с Figma попиксельно.
- **Полноэкранного режима нет.** Пробовали, но автоматический переход в полный экран неожиданен для игрока.
- **Панель инструментов** подстраивается под длину колонки. Карандаши уменьшаются, но не мельче ~32px, чтобы попадать пальцем.
- **Толщина и прозрачность** — повторное нажатие на выбранную кисть или карандаш открывает рядом карточку (так же, как повторное нажатие на цвет открывает палитру): три толщины и три прозрачности (100%, 60%, 30%) кружками текущего цвета, без ползунков — ребёнку проще попасть пальцем. У кисти и карандаша настройки свои; заливка удержанием берёт прозрачность. На ручке выбранного инструмента — точка текущей толщины и прозрачности. Полупрозрачные штрихи и заливки не накладываются: новый штрих замещает краску под собой (пересечения не темнеют, под штрихом остаётся только его цвет).
- **Кнопки холста** — над холстом слева от процента, а на телефоне в вертикальной раскладке — в верхней строке слева от камеры:
  - **сброс** очищает весь рисунок сразу, без подтверждения: это обычное действие, его отменяет кнопка «Отменить»;
  - **лупы «+» и «−»** (экраны от 1024px) — режим, а не разовое нажатие. Пока лупа включена, клик по рисунку приближает или отдаляет в эту точку, а перетаскивание двигает холст; рисовать в этом режиме нельзя. Повторное нажатие на лупу или выбор инструмента/цвета выключает режим, масштаб сохраняется;
  - **на экранах уже 1024px** (телефоны и большинство планшетов) вместо двух луп одна кнопка «Масштаб». Пока она включена, щипок двумя пальцами приближает и отдаляет, а один палец двигает холст; рисовать нельзя. Повторное нажатие или выбор инструмента/цвета выключает режим — один палец снова рисует в текущем масштабе. Вне режима второй палец ни на что не влияет, случайно приблизить рисунок во время раскраски нельзя.
  - Масштаб — от 1× до 3×.

**Экран входа.**
- **Быстрый вход.** Устройство помнит до 4 последних игроков. Если кто-то уже входил, под «Играть» есть кнопка «Быстрый вход»: она показывает список с флагами и именами, вход в одно нажатие. Под именем — когда игрок был здесь последний раз (страну показывает флаг): «сегодня», «вчера», «3 дня назад», «неделю назад»… (без «играл/играла»: пол игрока неизвестен). Время обновляется при входе и при выходе из аккаунта — иначе игрок, который вошёл неделю назад и играл до сегодня, выглядел бы давно ушедшим. Новые сверху, самый старый вытесняется; «×» забывает игрока на этом устройстве. Выход из аккаунта список не очищает — для того он и нужен.
- **Как устроено.** В cookie `quick_login` лежат только имя, страна и время последнего визита на этом устройстве, по нажатию уходит обычный запрос входа. Защиту это не ослабляет: вход и так без пароля, имени и страны для него достаточно. Cookie, а не `localStorage` — чтобы сервер видел список и кнопка была в HTML сразу, без «прыжка» после загрузки. Путь у cookie — `/`, хотя нужна она только экрану входа: Chrome показывает в `document.cookie` cookie с путём `/login` только если вкладку открыли на `/login`. Если открыли галерею и потом вышли, экран входа видел пустой список и затирал его. Цена — до ~0,7 КБ в каждом запросе. Содержимое cookie проверяется теми же правилами, что и форма входа, подменённые записи отбрасываются.

**Галерея.**
- **Компьютер.** По 12 карточек на странице: карточка импорта и 11 артов. Номер страницы хранится в адресе, следующая подгружается заранее.
- **До 680px** вместо пагинации лента экранов со свайпом и точками.
- **Импорт.** Свои SVG появляются первыми, удаляются с подтверждением, не больше 50 штук.
- **Слева сверху** — кнопки выхода из аккаунта и музыки. Выход ведёт на экран входа; чтобы вернуться к своим рисункам, достаточно снова войти с тем же именем и страной или через «Быстрый вход».
- **Значок «Новое»** — на арте, опубликованном из админки. Держится, пока игрок его не открыл, но не дольше 14 дней.

**Импорт SVG.** Подходят Figma-рисунки пером и фигурами, а также трассированные картинки.
- Цвета не переносятся: раскраска начинается с чистого листа.
- Фон фрейма Figma убирается, тонкие линии утолщаются.
- Разрывы в линиях до ~6px закрываются.
- Ошибки понятные: не SVG, больше 1 МБ, нет размера, слишком вытянутый, больше 5000 фигур, только текст.

**Админка.**
- **Загрузка SVG.** Новый арт сначала черновик. Админ видит контур и «области для раскраски» в той же разметке, что у игрока, и публикует.
- **Статусы:** черновик → опубликован → скрыт. Рисунки игроков на скрытом арте сохраняются и возвращаются, если опубликовать арт снова. Удалить можно только черновик.
- **«Кому показывать»:** всем или выбранным странам и игрокам. Арт виден, если подходит страна **или** игрок есть в списке. Правило видимости одно — и для галереи, и для всех запросов рисунка.
- **Статистика** за 7 дней, 30 дней или всё время, с фильтром по стране: сколько игроков открыли арт, начали, завершили, какая доля доводит до конца. Каждый игрок считается один раз.
- **Страница игрока:** его рисунки. Каждый можно открыть в полном размере: его собирает тот же движок из истории на сервере. Картинку можно скачать.
- **Админка — обычный сайт:** прокрутка, выделение, масштаб. На узком экране — бургер-меню.

**«Нативность» игры.** Нет прокрутки страницы, pull-to-refresh, выделения, зума, перетаскивания картинок и меню по долгому тапу.

## Известные ограничения

- **Вход без пароля** (требование ТЗ): кто знает имя и страну игрока, тот войдёт под ним. На общем устройстве «Быстрый вход» показывает имена тех, кто на нём играл, — лишнее имя убирается «×».
- **Офлайн неполный.** Без сети сохраняется работа в уже открытом рисунке. Открыть новый арт или галерею без сети нельзя.
- **Импорт SVG:**
  - разрывы в линиях шире ~6px не закрываются, и область сливается с соседней;
  - большая тёмная фигура становится линией, а не областью;
  - текст и вставленные картинки пропускаются.
- **Сохранение в галерею телефона** — только через системное «Поделиться»: браузер не может сохранить без подтверждения.
- **Новая публикация** появляется у игрока после обновления галереи или в пределах 5 минут — столько живёт кэш.
- **Опубликованный арт нельзя удалить из админки**, только скрыть. Удаление — вручную в базе: строку из `coloring_arts` удалить можно, рисунки игроков удалятся каскадом.
- **Открытия** считаются с момента появления админки (22.10.2026). Начала и завершения — за всё время.
- **Базовые арты** — PNG.
- **Приближение размывает краску:** бумага рисунка хранится в фиксированном разрешении (от него зависят координаты истории), поэтому масштаб ограничен 3×.
- **Картинки рисунков** (база и миниатюры) хранятся в Postgres (`bytea`).
- **Автотесты** проверяют логику без браузера. Сценарии в браузере (Playwright) прогонялись при разработке, но в репозиторий не входят.

## Что сделано с помощью ИИ и как результат проверялся

Проект сделан с ИИ-ассистентом Claude Code (Anthropic).
- **Разработчик:** ставил задачи, принимал продуктовые решения (ориентация телефона, поведение панелей, фактура карандаша, модель назначения артов, правила статистики), проверял результат в браузере и возвращал на доработку.
- **ИИ:** писал код, искал причины ошибок, готовил скрипты проверки.

Каждое изменение проверялось так:
- **Сверка с макетом.** Экраны сравнивались с фреймами Figma попиксельно (Playwright + pixelmatch).
- **Сценарии в браузере** (Playwright, из временной папки вне проекта):
  - **рисование:** штрих только внутри сегмента, заливка и очистка удержанием, отмена и повтор, перезагрузка с сохранённой историей, обрыв сети и досылка;
  - **галерея:** пагинация, свайп, совпадение SSR и клиентской раскладки;
  - **импорт SVG;**
  - **админка:** доступ, загрузка, публикация, назначение по стране и игроку, скрытие с сохранением рисунков, статистика;
  - **просмотр рисунка игрока в админке** совпал с холстом игрока до пикселя.
- **Нагрузка:**
  - 150 каракулей на одном арте — долгих задач не прибавилось, кадры ≤ 17 мс;
  - 72 параллельных запроса к API — так нашлась ошибка конвейера `postgres.js`.
- **Безопасность.** Обходы путей админки, подбор пароля, вредоносные SVG. В прод-сборке нет строки подключения к базе, а `svgo` не попал в клиент.
- **Рефакторинг:**
  - детектор копипасты `jscpd` — 0 повторов;
  - неиспользуемых экспортов нет;
  - удаление комментариев проверено сравнением токенов TypeScript «до» и «после».
- **Автотесты** — см. ниже. Проверка типов и прод-сборка — на каждом этапе.

## Что улучшил бы при наличии времени

- **Тесты:** перенести браузерные сценарии (Playwright) в репозиторий и CI, добавить визуальную сверку с макетом. Интеграционные тесты обработчиков с тестовой базой: видимость артов, конфликты 409/413, «запекание» истории.
- **Офлайн и устройства:** полноценный офлайн-режим (PWA, Service Worker) и слияние истории при работе с двух устройств — по идентификаторам операций вместо «последнее сохранение побеждает».
- **Хранение и сервер:**
  - картинки рисунков — в объектное хранилище (Supabase Storage) с CDN вместо `bytea`;
  - ограничение частоты для входа игроков и импорта;
  - CSP для всего приложения;
  - чистка просроченных сессий по расписанию;
  - приватный канал Realtime для сигнала галереи: политика RLS на `realtime.messages` разрешает роли `anon` только чтение, и отправить сигнал может только сервер. Сейчас канал публичный, и защищает ограничение частоты на клиенте.
- **Производительность:** разметку больших SVG — в Web Worker. Сейчас она идёт в основном потоке, около 100–200 мс на сложной картинке.
- **Админка:**
  - удаление опубликованного арта с предупреждением о рисунках игроков;
  - порядок артов в галерее;
  - графики статистики по дням и экспорт в CSV;
  - журнал действий администраторов.
- **Игрок:** способ вернуть аккаунт, если игрок забыл имя.
- **Доступность и языки:** проверка доступности с экранным диктором, другие языки интерфейса.
